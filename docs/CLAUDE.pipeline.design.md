# shared/pipeline.md — ① 파이프라인 방법론 (Pipeline Methodology)

> **이 파일의 위치**: 여러 agent adapter가 공통으로 읽는 `shared/` 구조 중 첫 번째.
> ① 파이프라인 방법론(이 파일) · ② 앱인토스 플랫폼 규칙 · ③ 앱별 컨텍스트
>
> **이 파일이 정의하는 단계·게이트·검수 규칙은 앱·플랫폼이 바뀌어도 재사용한다.** 건강폰술이라는 특정 앱, 앱인토스라는 특정 플랫폼에 종속된 내용은 여기에 쓰지 않는다. 그런 내용은 ②·③ 파일로 분리한다. 이 분리가 파이프라인 재사용성의 핵심이며, 본 프로젝트의 평가 대상이다.

---

## 0. 목적과 범위

이 파이프라인은 **하나의 앱을 만드는 절차가 아니라, 다양한 아이디어를 앱으로 구현하기 위한 재사용 가능한 AI 기반 개발 절차**다. 중심 실행체는 코딩 에이전트이며, 각 단계 사이에 사람이 검수하는 게이트(human review gate)를 둔다.

- **평가 대상**: 산출된 앱이 아니라, 이 파이프라인이 다음 아이디어에도 적용 가능한가(재사용성).
- **성공 기준**: 새 아이디어가 들어왔을 때, ① 파일의 단계·게이트·검수 규칙은 유지하고, 앱 고유 정보는 ③ 앱별 컨텍스트를 교체하는 방식으로 확장 가능해야 한다. 플랫폼이 바뀌는 경우에는 ② 플랫폼 규칙을 교체하되, ①의 방법론 구조는 유지한다.
- **재사용성의 의미**: 같은 입력에 같은 출력이 나오는 재현성이 아니라, **다양한 입력·플랫폼에 유연하게 적응**하는 것. 동적 워크플로우의 적응성은 위험이 아니라 재사용성을 실현하는 메커니즘이다.

---

## 1. 파이프라인 원칙

### 1.1 What은 고정, How는 위임
- 이 파일은 **무엇(what)** 을 정의한다: 단계, 역할, 각 단계의 입력·출력·수용 기준, 정책 가드레일.
- **어떻게(how)** — 구체적 구현 방법 — 는 코딩 에이전트의 동적 판단에 위임한다.
- 단계에 도구를 배치하는 것(stage-tool 매핑)은 what에 속한다. 그 도구가 내부에서 어떻게 일하는지는 how다.

### 1.2 최적화 우선순위
1. **(B) 인간 개입 최소화** — 사람의 손이 꼭 필요한 지점(가정·검증불가·되돌리기 어려움)에만 개입이 걸리도록 설계한다.
2. **(D) 전환 비용 최소화** — 다음 아이디어로 갈아끼울 때 드는 세팅 비용을 줄인다.
- 두 목표가 충돌하면 B를 우선한다.

### 1.3 도구는 단계가 요구하면 쓰고, 아니면 줄인다
- 도구를 늘릴수록 전환 비용·일관성 관리 비용이 커진다(1.2의 B·D 둘 다 악화).
- 중심 실행 루프(기획 해석 → 구현 → 테스트 → 검수)는 **하나의 중심 코딩 에이전트**로 통일한다.
- 코딩 에이전트가 구조적으로 못 하는 일(사용자 경험 자산 생성, 실제 실행 환경에서의 동작 확인)에만 별도 도구/사람을 붙인다.

---

## 2. 단계 정의 (Stages)

각 단계는 **입력 → 작업 → 출력 → 수용 기준(Definition of Done)** 으로 정의한다. how는 명시하지 않는다.

| 단계 | 입력 | 출력 | 수용 기준 |
|---|---|---|---|
| **S1 기획·스펙 해석** | 아이디어, 플랫폼 공식 문서 | 기능정의서, 화면설계서, 데이터 구조 | 스펙이 문서 근거를 갖고, 화면 흐름·상태·전환이 끝까지 확정됨 |
| **S2 구현** | S1 산출물 + ②·③ 파일 | 동작하는 코드 | 스펙 충족, 금지사항 미위반, 검수 마커 표기 완료 |
| **S3 테스트** | S2 코드 | 단위·통합 테스트 결과 | 핵심 인터랙션 통과, 대상 실행 환경에서 플랫폼 의존 기능 동작 확인 |
| **S4 검수** | S2·S3 산출물 | 검수 통과 또는 수정요청 | 모든 검수 마커가 사람에 의해 해소됨, AI 생성 흔적 및 UX 자연성 점검 통과 |
| **S5 배포** | S4 통과물 | 배포본, 제출 산출물 | 플랫폼 검수 요건 충족, 되돌리기 어려운 값 사람 확인 |

> 각 단계의 **구체적 입출력 항목**은 ③ 앱별 컨텍스트에서 채운다. 이 표는 골격이다.

---

## 3. Stage-Tool 매핑

| 단계 | 도구 | 비고 |
|---|---|---|
| S1 기획·스펙 해석 | 중심 코딩 에이전트 | 중심 루프 |
| S2 구현 | 중심 코딩 에이전트 | 중심 루프 |
| S3 테스트(코드) | 중심 코딩 에이전트 | 중심 루프 |
| S3 플랫폼 의존 기능 검증 | 사람 + 대상 실행 환경 | 코드가 대신 못 봄 |
| 사용자 경험 자산이 필요한 경우 | 사람 선별 → 생성 AI 또는 공개 라이선스 자산 보강 | 필요할 때만 사용 |
| S4 검수 / 자산 일관성·라이선스 | 사람 | 항상 |
| 문서·매뉴얼 초안 | 중심 코딩 에이전트 | 중심 루프 |
| 협업 인프라 (Git·Notion·WBS) | — | AI 도구 아님, 별도 층 |

> **이 매핑은 기본값이다.** 새 아이디어의 자산 유형이나 플랫폼 제약 때문에 도구 변경이 필요한 경우, ① 파일의 구조를 바꾸지 않고 변경 사유를 별도 기록한다. 기본 태도는 "단계가 요구하면 쓰고 아니면 줄인다".

---

## 4. Human Review Gate (검수 게이트)

단계와 단계 사이에 사람의 승인 지점을 둔다. 게이트를 통과하지 못하면 다음 단계로 가지 않는다.

### 4.1 게이트 원칙
- AI의 실수는 팀의 책임이다. 따라서 **사람이 판단해야 할 지점이 사람 눈에 반드시 띄도록** 만드는 것이 게이트의 목적이다.
- 게이트는 "AI가 일을 잘했는가"가 아니라 "**사람이 책임질 판단이 무엇인지 드러났는가**"를 본다.

### 4.2 검수 마커 규칙
에이전트는 다음 **세 조건 중 하나에 해당할 때만** 마커를 단다. 셋 다 아니면 마커 없이 진행한다.

| 마커 | 조건 |
|---|---|
| `// UNVERIFIED:` | ① 공식 문서로 검증하지 못한 외부 동작 (SDK 거동, 플랫폼 정책 경계, 라이브러리 동작) |
| `// ASSUMPTION:` | ② 스펙·문서에 없어 에이전트가 임의로 정한 값·동작 (수치, 환산 계수, 미명세 엣지케이스) |
| `// REVIEW(사유):` | ③ 되돌리기 어렵거나 사용자에게 그대로 노출되는 것 (변경 불가 값, 사용자 노출 문구·톤, 배포 설정) |

> 평범하게 검증된 코드(상태관리, 일반 로직, 명세대로 구현한 부분)에는 마커를 달지 않는다. 마커 목록이 곧 "이번 단계에서 팀이 책임질 판단의 전부"가 되도록 좁게 유지한다.

작업 완료 후 마커를 모아 **검수 체크리스트**로 출력한다.

---

## 5. 작업 전 의도 선언 규칙

모든 구현·수정 작업을 **시작하기 전에** 다음을 먼저 출력한다. 결과물이 아니라 판단을 검수할 수 있게 하기 위함이다.

- **목표**: 이 작업이 충족하려는 스펙/요구사항 (출처 문서·조항 명시)
- **접근**: 택한 방법과 대안, 그중 이것을 고른 이유
- **가정**: 문서에 없어 임의로 정한 사항 (← 사람이 반드시 확인할 지점)
- **영향 범위**: 건드리는 파일·기능

> AI의 실수는 대부분 "명시되지 않은 것을 임의로 메운" 지점에서 나온다. 가정을 분리해 명시함으로써 그 지점에 사람의 눈을 강제로 끌어온다.

---

## 6. 버전 관리 · 커밋 규약

### 6.1 프롬프트 버전 관리
- 단계별 프롬프트는 `/prompts` 폴더에 저장하고 Git으로 버전 관리한다.
- 프롬프트 변경 이력 자체가 파이프라인의 재사용 자산이다.

### 6.2 커밋 규약 (AI 작업과 사람 작업 구분)
| 접두사 | 의미 |
|---|---|
| `ai:` | AI가 생성한 상태 — **사람 검수 전** |
| `review:` | 사람이 검수·수정한 상태 — 검수 통과 또는 수정 반영 |

> **`ai:` 커밋만 있는 변경은 머지·배포하지 않는다.** 검수 게이트를 커밋 단위에서 강제하는 장치다.

---

## 7. 단계 완료 보고 규칙

각 단계 종료 시 에이전트는 다음을 보고한다 (Definition of Done에 검수 항목 포함).

- **한 일 요약**: 스펙 대비 충족 / 미충족 항목
- **검수 필요 지점**: §4.2 마커 집계
- **사람이 판단해야 할 부분**: AI가 확신하지 못하는 지점
- **AI 생성 흔적 및 UX 자연성 위험 지점**: 부자연스러운 UX 문구, 틀에 박힌·일반적 처리 등 (AI 한계가 용인되지 않음 — AI 생성 흔적이 드러나지 않아야 함)

---

## 8. 새 아이디어로 재사용하는 절차

이 파이프라인을 다른 앱에 적용할 때:

1. 이 ① 파일의 단계·게이트·검수 규칙은 **그대로 유지한다.**
2. ② 플랫폼 규칙 파일을 대상 플랫폼에 맞게 교체한다.
3. ③ 앱별 컨텍스트 파일을 새 아이디어로 새로 쓴다.
4. §3 stage-tool 매핑은 기본값으로 두되, 새 아이디어의 자산 유형·플랫폼 제약 때문에 도구 변경이 필요하면 **구조를 바꾸지 않고 변경 사유만 별도 기록**한다.
5. S1부터 게이트를 따라 진행한다.

> 갈아끼우는 데 드는 작업이 ②·③ 두 파일 교체 + (필요시) 도구 변경 사유 기록뿐이라면, 전환 비용 최소화(D)가 달성된 것이다.
