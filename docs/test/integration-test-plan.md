## 1. 목적

화면, 상태 저장, 오디오·햅틱, 토스 SDK, 센서 및 실시간 서버를 연결한 사용자 흐름을 검증한다. jsdom 통합 자동화와 실제 대상 환경 검증을 구분해, mock 통과를 실기기 통과로 오인하지 않도록 한다.

## 2. 대상 구성

```text
React 화면/상태
  ├─ 앱인토스 SDK: Storage, share, getTossShareLink, closeView, haptic
  ├─ WebView: visibilitychange, Audio, DeviceMotion
  └─ 실시간 서버: POST /rooms, POST /rooms/{code}/close, wss /ws/{code}
```

## 3. 환경

| 레벨 | 환경 | 목적 |
|---|---|---|
| L1 | Vitest + jsdom | 화면·스토어·라우팅 통합 회귀 |
| L2 | 로컬/배포 브라우저 + staging 서버 | REST/wss 계약, 2개 클라이언트 동기화 |
| L3 | 앱인토스 샌드박스 Android/iOS 실기기 | SDK, WebView, 센서, 무음·백그라운드, 성능 최종 확인 |

L3는 최소 Android 1대와 iOS 1대에서 수행하고 OS·기기·네트워크를 결과서에 남긴다.

## 5. 실시간 서버 계약 검증 절차

1. staging `/health`가 `{ status: "ok" }`를 반환하는지 확인한다.
2. 기기 A에서 방을 생성하고 코드·host token이 로그/분석 도구에 노출되지 않는지 확인한다.
3. 기기 B가 코드로 접속하면 양쪽 roster가 2명으로 갱신되는지 확인한다.
4. A와 B가 각각 짠을 보내 양쪽에 1회씩 수신되는지 타임스탬프로 기록한다.
5. 연타 쿨다운, 참여자 leave, 우발적 단절/재연결을 확인한다.
6. 방장 종료 후 양쪽이 room_closed를 받고 더 이상 재연결하지 않는지 확인한다.
7. 서버 로그에서 실명·연락처·토스 식별값과 host token 원문이 저장되지 않는지 확인한다.

## 6. 성능 측정

- 초기 로딩: 앱 진입 시작부터 첫 조작 가능 화면까지 3회 측정해 최대값을 기록한다.
- 반응 시간: 따르기 시작, 비우기, 짠 수신 각각 입력/수신부터 첫 시각 변화까지 측정한다.
- 실시간 짠 지연: 서버 송신과 두 클라이언트 표시 시각을 기록하며 목표는 수백 ms, 필수 상한은 2초로 둔다.
- 네트워크: Wi-Fi와 이동통신 또는 네트워크 제한 조건을 각 1회 포함한다.

## 7. 진입·종료 기준

### 진입 기준

- 단위 테스트 P0 통과 및 Major 결함 조치
- 프런트 빌드 성공
- staging 서버 endpoint가 환경변수로 주입됨
- 앱인토스 샌드박스 빌드와 테스트 기기 준비

### 종료 기준

- P0 시나리오 100% 수행 및 Critical/Major 미해결 0건
- L3에서 F-SY-03/04/05/06/07/08 확인
- 두 실기기에서 방 생성·참여·roster·짠·종료·재연결 확인
- `UNVERIFIED`와 `REVIEW` 항목에 사람 승인 또는 차단 사유 기록
- 음주 대체 톤·비게임 정책 사람 검수 완료

## 8. 산출 증적

- 명령 로그와 테스트 러너 결과
- 기기/OS/앱 빌드/서버 버전
- 시나리오별 화면 녹화 또는 스크린샷
- 성능 측정 원시값
- 서버 로그의 민감정보 비저장 점검표
- 결함 목록과 재시험 결과
